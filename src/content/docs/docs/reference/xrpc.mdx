[XRPC](https://atproto.com/specs/xrpc) is the HTTP-based RPC protocol atproto uses. HappyView registers XRPC endpoints from your [lexicons](/docs/getting-started/lexicons), whether they come from a project, an upload or the network: query lexicons become `GET /xrpc/{nsid}` routes, procedure lexicons become `POST /xrpc/{nsid}` routes.

A query or procedure is served by the [script](/docs/getting-started/scripts) attached to it. Without one, a query answers only a single-record lookup by `uri`, and every other call answers [`501`](#method-has-no-script).

## Auth

XRPC routes accept DPoP auth, service auth JWTs, space credentials, the dashboard's session cookie, or no authentication at all. The [authentication reference](/docs/reference/authentication#authenticating-users-for-procedures) owns each method's headers and the order HappyView tries them in. Admin API keys (`hv_*`) are refused on XRPC routes. An anonymous request leaves `ctx.caller_did` absent in scripts.

Default auth behavior:

- **Queries** (`GET /xrpc/{method}`): unauthenticated by default, with the caller's identity available if provided.
- **Procedures** (`POST /xrpc/{method}`): require authentication.
- **getProfile** and **uploadBlob**: require authentication.

A request with an identity also has to name its API client, with `X-Client-Key` or `client_key`. A request is charged to that client's rate-limit bucket only when it proves it is that client; otherwise it is rate limited as anonymous. See [API client identification](/docs/reference/authentication#xrpc-api-client-identification).

## Fixed endpoints

These endpoints are always available regardless of which lexicons are loaded.

| Endpoints | Documented in |
| --- | --- |
| `GET /health`, `GET /xrpc/app.bsky.actor.getProfile`, `POST /xrpc/com.atproto.repo.uploadBlob` | This page |
| `dev.happyview.listApiClients`, `getApiClient`, `createApiClient`, `deleteApiClient` | [Third-party API clients](/docs/reference/oauth) |
| `dev.happyview.delegation.*` | [Delegation](#delegation) |
| `com.atproto.space.*`, `com.atproto.simplespace.*` | [Spaces](/docs/guides/spaces), while spaces are turned on |

### Delegation

`dev.happyview.delegation.*` are the methods that link accounts and manage who may write for them. A write under a delegated account passes `delegateDid`, and the script sees it as `ctx.delegate_did`.

| Method | Type | Parameters or body | Success |
| --- | --- | --- | --- |
| `dev.happyview.delegation.linkAccount` | procedure | `did` | `201` with `{ did }` |
| `dev.happyview.delegation.unlinkAccount` | procedure | `did` | `200` with `{}` |
| `dev.happyview.delegation.addDelegate` | procedure | `accountDid`, `userDid`, `role` (`admin` or `member`) | `201` with `{}` |
| `dev.happyview.delegation.removeDelegate` | procedure | `accountDid`, `userDid` | `200` with `{}` |
| `dev.happyview.delegation.listAccounts` | query | none | `200` with `{ accounts }` |
| `dev.happyview.delegation.getAccount` | query | `did` | `200` with `{ did, role, linkedBy, createdAt }` |
| `dev.happyview.delegation.listDelegates` | query | `accountDid` | `200` with `{ delegates }` |

### Get profile

```
GET /xrpc/app.bsky.actor.getProfile
```

Returns the authenticated user's profile, read from their PDS. A service auth JWT isn't accepted here.

interface ProfileResponse {
  did: string;
  handle: string;
  displayName?: string;
  description?: string;
  avatarURL?: string;

## Dynamic query endpoints

Query endpoints are generated from lexicons with `type: "query"`. The method's [script](/docs/getting-started/scripts) handles every call and decides what the response is. A query with no script answers one call, a single-record lookup by `uri`; any other call answers [`501`](#method-has-no-script).

### Single record

```
GET /xrpc/{method}?uri={at-uri}
```

## Dynamic procedure endpoints

Procedure endpoints are generated from lexicons with `type: "procedure"`. The method's [script](/docs/getting-started/scripts) handles the call: it validates the body, writes whatever records it writes, and returns the response. A procedure with no script answers every call with [`501`](#method-has-no-script); HappyView writes nothing to the caller's PDS on its own.

### Method has no script

A query called without a `uri`, or a procedure called at all, with no script attached answers `501 Not Implemented`:

```json
{
  "error": "MethodNotImplemented",
  "message": "xyz.statusphere.setStatus has no script. Add one for the trigger xrpc.procedure:xyz.statusphere.setStatus"
}
```

For a query, the trigger in the message is `xrpc.query:<method>`. Add a script for that trigger; it names the collection it reads or writes. See [Queries and procedures need a script](/docs/reference/lexicons#queries-and-procedures-need-a-script).

## Request validation

HappyView checks each call to a dynamic endpoint against its lexicon before a script runs. A call that breaks the lexicon gets `400` with the error `InvalidRequest`. [Lexicon checks](/docs/getting-started/queries-and-procedures#lexicon-checks) lists what's checked.

## XRPC proxy

A request for an NSID with no lexicon on the instance falls through to the proxy. The proxy's mode decides whether the method may be proxied, and its routing decides where it goes. See [XRPC routing for unknown methods](/docs/reference/lexicons#xrpc-routing-for-unknown-methods) and [XRPC proxy settings](/docs/reference/admin/xrpc-proxy).

## Errors

Error responses return JSON with an `error` field, and many also carry a `message`:

```json
{
  "error": "description of what went wrong"
}
```

| Status | Meaning | Common causes |
|--------|---------|---------------|
| `400 Bad Request` | Invalid input | Missing required fields, malformed JSON, invalid AT URI, an error the method's lexicon declares |
| `401 Unauthorized` | Authentication failed | Missing client identification, or invalid DPoP or service authentication |
| `403 Forbidden` | Refused | The proxy policy doesn't allow the NSID |
| `404 Not Found` | Method or record not found | The requested record doesn't exist, or the feature is turned off |
| `408 Request Timeout` | A script ran out of time | See [Script errors](#script-errors) |
| `429 Too Many Requests` | Rate limited | The bucket the request is charged to is empty: its API client's, once proven, otherwise the shared anonymous one |
| `500 Internal Server Error` | Server-side failure | Script error, database error, or upstream PDS failure |
| `502 Bad Gateway` | Upstream failure | The [XRPC proxy](#xrpc-proxy) couldn't resolve or reach the method's authority |
| `501 Not Implemented` | Method has no script | A query or procedure lexicon with no script attached; see [Method has no script](#method-has-no-script) |
| `503 Service Unavailable` | Storage unavailable | The storage that holds the collection is down |

### Script errors

When a script fails, the response is a `script_error` body:

```json
{ "error": "script_error", "errorType": "runtime", "message": "attempt to index a nil value (local 't')", "method": "xyz.statusphere.getStatus", "line": 3, "file": "src/lib/format.lua" }
```

`errorType` is `syntax`, `runtime`, `memory` or `missing_handle` with status `500`, or `timeout` with status `408` when the script hit the instruction limit or the wall clock, both set in **System > General**. `line` is the script line that raised, or `null`. `file` is the project file `line` is in, relative to the project root: the script itself, or a local module it imported. It is `null` for a script saved through the dashboard, which has no file.

The instance logs the same error with the script source and the caller's input. See [Errors](/docs/reference/scripts/contract#errors) for how to diagnose script issues.

### PDS errors

When a procedure proxies a write to the user's PDS and the PDS returns an error, HappyView forwards the PDS response status code and body directly to the caller.
