| Field               | Type    | Required | Description                                                           |
| ------------------- | ------- | -------- | --------------------------------------------------------------------- |
| `lexicon_json`      | object  | yes      | Raw lexicon JSON (must have `lexicon: 1` and a valid NSID `id`)       |
| `backfill`          | boolean | no       | Whether the first upload triggers a historical backfill (default `true`) |
| `target_collection` | string  | no       | For query/procedure lexicons, the record collection they operate on   |
| `action`            | string  | no       | For procedure lexicons, what the procedure does to its collection: `create`, `update`, `delete` or `upsert`. Left out, it's `upsert`, which decides by whether the input has a `uri`. Anything else is `400` |
| `token_cost`        | integer | no       | Token cost for query/procedure endpoints (overrides instance default) |
| `indexed`           | boolean | no       | For record lexicons, whether HappyView ingests the collection. Defaults to `true` for a new lexicon; left out on an update, the stored setting is kept. An unindexed lexicon starts no backfill |

The `id` must be a valid [NSID](https://atproto.com/specs/nsid). It is the
lexicon's primary key, the XRPC method it is served at, and, for record
lexicons, the collection HappyView filters Jetstream on. An `id` that is empty
or malformed is rejected with `400 Bad Request`, and an `id` a project file
defines with `409 Conflict`.

**Response**: `201 Created` (new) or `200 OK` (upsert)

```json
{
  "id": "xyz.statusphere.status",
  "revision": 1,
  "backfill_job_id": "9f1c8e2a-7b40-4d1e-9f3a-2c5b8d6e1a04",
  "issues": []
}
```

`backfill_job_id` is the id of the [backfill job](/docs/reference/admin/backfill) this upload
started, or `null` if it started none: because `backfill` was `false`, because
this was an upsert rather than a first upload, because the lexicon is not an
indexed record type, or because the caller lacks `backfill:create`. Poll it via
`GET /admin/backfill/status`.

`issues` lists any warnings about the document, and is empty when there are none.

### Validation

The document is checked against the lexicon spec before anything is stored. A
document that can't work is refused with `400 Bad Request` and one entry per
problem:

```json
{
  "error": "the lexicon is not valid: defs.main.key: unknown record key 'uuid': must be tid, nsid, any, or literal:<value> (and 2 more)",
  "issues": [
    {
      "path": "defs.main.key",
      "message": "unknown record key 'uuid': must be tid, nsid, any, or literal:<value>",
      "severity": "error"
    },
    {
      "path": "defs.main.record.properties.a.ref",
      "message": "'#missing' names no def in this lexicon ('missing' is not defined)",
      "severity": "error"
    }
  ]
}
```

| Field | Type | Description |
| --- | --- | --- |
| `path` | string | Dotted path into the document, with array entries as `required[0]`. Empty for a problem with the document as a whole, such as its size |
| `message` | string | What's wrong |
| `severity` | string | `error` or `warning` |

Only an `error` refuses the upload. A `warning` is a document that works but
reads oddly, such as an `array` with no `items`, and it's reported beside the
errors. An upload whose only issues are warnings succeeds and carries them in
`issues` on its response.

A `subscription` lexicon is valid and gets a warning: it's stored, and no
endpoint is generated for it, because HappyView doesn't serve subscriptions.

The check covers the `lexicon` version and the `id` NSID; that `defs` is a
non-empty object; that every def names a known type; that `record`, `query`,
`procedure` and `subscription` appear only as `main`; that a record says how its
rkey is chosen (`tid`, `nsid`, `any` or `literal:<value>`) and carries an object
schema; that a `ref` or `union` member naming a def in this document resolves
(a ref into another lexicon is checked only for shape); that an object's
`required` and `nullable` name properties it has; and that the document is at
most 256 KiB.

**Response**: `204 No Content`

Deleting a lexicon stops live indexing and leaves the records already indexed under its collection in place. To delete those too, add `delete_records=true`:

```
DELETE /admin/lexicons/{id}?delete_records=true
```

This also needs `records:delete-collection` and `records:delete`, like [deleting a collection](/docs/reference/admin/records#delete-all-records-in-a-collection). The response is then `202 Accepted`:

```json
{
  "job_id": "0f9f1c8e-7b40-4d1e-9f3a-2c5b8d6e1a04",
  "collection": "xyz.statusphere.status"
}
```

The records are deleted by a `happyview.delete-collection` [job](/docs/reference/admin/jobs). The lexicon is removed before the job is enqueued, so live indexing can't put records back while it runs. Records a record script kept after the source deleted them are included.

`delete_records=true` returns `400 Bad Request` for anything but a record lexicon, because a query or procedure lexicon operates on another lexicon's collection, and for a collection served from a shared record store. The lexicon is left in place when the request is refused.

Deleting a lexicon listed under `[network_lexicons] include` in `happyview.toml` returns `409 Conflict`.

## Lexicons a project file defines

When the instance runs a project, a lexicon defined by a file under `src/` answers ahead of any stored row with the same id. Uploading, deleting, adding as a network lexicon or removing as one is refused with `409 Conflict`:

```
{ "error": "defined by the project file src/lexicons/com/example/thing.json; change that file instead" }
```

A stored row the file shadows is kept as it is and answers again when the file is removed.

### Preview a network lexicon

```
GET /admin/network-lexicons/resolve/{nsid}
```

Resolves an NSID's lexicon from its authority on the network and returns it, without tracking it. The dashboard uses this to show a lexicon before you add it. Requires `lexicons:read`.

**Response**: `200 OK`

```json
{
  "nsid": "xyz.statusphere.status",
  "authority_did": "did:plc:…",
  "type": "record",
  "lexicon_json": { "lexicon": 1, "id": "xyz.statusphere.status", "defs": {} }
}
```

`type` is the lexicon's `defs.main.type`, or `null` if it has none. A lexicon that can't be resolved is an error; [Lexicons](/docs/reference/lexicons#nsid-authority-resolution) describes the lookup.

Removes the network lexicon tracking and also deletes the lexicon from the `happyview_lexicons` table and in-memory registry.

A network lexicon listed under `[network_lexicons] include` in the project's `happyview.toml` reports `declared: true`, and removing it returns `409 Conflict`; remove it from the file instead.
