## Scripts and plugins

### Script

Code that runs on your instance when something happens: an XRPC query or
procedure is called, a record or label arrives, or a job runs. Every script
defines `handle(input, ctx)`. `input` is what the trigger passes (a query's
parameters, a procedure's body, the record event). `ctx` carries the caller
and the run's context. A script loads what it needs with `require`. Scripts
are written in a language an installed [interpreter](#interpreter) runs: Lua,
JavaScript or TypeScript.

v2's script globals (`db`, `Record`, `params` and 29 others) are gone in v3.
See [Migrating scripts to v3](/docs/guides/migrating-scripts).

### Trigger

What makes a [script](#script) run, written as an id such as
`record.create:xyz.statusphere.status`. A script is named by what triggers it:
a **query script** (`xrpc.query`), a **procedure script** (`xrpc.procedure`), a
**record script** (`record.index`, `record.create`, `record.update` or
`record.delete`), a **label script** (`labeler.apply`) or a **job script**
(`job.run`).

### Script variable

A named value a [script](#script) reads from `ctx.env`, managed on the
dashboard's **ENV Variables** page. It isn't an environment variable, which
configures the [instance](#instance).

### Language

What a [script](#script) is written in: Lua, JavaScript or TypeScript. Each is
run by its own [interpreter](#interpreter).

### Interpreter

A [plugin](#plugin) that runs scripts in one language. HappyView ships
without one, so until you install one, no script can be saved or run. The
official interpreters are `happyview-lua`, `happyview-javascript` and
`happyview-typescript`. Each claims a language ID (`lua`, `javascript`,
`typescript`); a script runs on the interpreter that claims its language.

### Library

A [plugin](#plugin) that gives scripts an API, loaded with `require`:
`require("happyview.db")` for querying records, for example. Libraries are
installed separately from interpreters, and an interpreter declares which
libraries it supports. The `internal.` namespace (`internal.json`,
`internal.logging` and so on) is reserved for modules the
[interpreter](#interpreter) provides itself.

### Plugin

A WebAssembly module that extends HappyView. There are three types:
[interpreters](#interpreter), [libraries](#library) and **auth** plugins,
which link accounts on other platforms. A plugin's manifest must declare
`api_version` `"2"` and list its [capabilities](#capability); HappyView refuses
anything else. You install plugins from the [registry](#registry), from a URL,
or from a file.

### Auth plugin

A [plugin](#plugin) that lets a [user](#user) link an account on another
platform, such as Steam or itch.

### Capability

Something a [plugin](#plugin) is allowed to do, such as `records:read`,
`network:request` or `secrets:read`. A plugin's manifest lists the
capabilities it needs. HappyView checks that list against what the plugin's
code actually imports, refuses a plugin that imports more than it declares, and
shows you the list to approve when you install it. Each capability carries a
risk level, from low to critical.

## Getting plugins

### Registry

Where HappyView finds plugins to install. The registry is a set of
`software.release` atproto records: a **project** per plugin
(`software.release.project`), with its **versions** (`software.release.version`).
A project is named by its publisher's DID plus a name, for example `happyview-lua`.
HappyView reads the registry at `https://api.happyproto.at` and refreshes its
registry listing every 15 minutes. `PLUGIN_REGISTRY_URL` points it elsewhere, or `off`
stops HappyView reading the registry.

A registry install is checked by CID: HappyView fetches the plugin's manifest
and module from the registry, refuses any bytes whose CID doesn't match, and
fetches them again at every startup and reload. Updates only ever come from
the publisher you installed from.

### Channel

A line of releases a plugin publishes in the [registry](#registry): `latest` for
releases, `beta` and `alpha` for prereleases. An install follows a channel,
and is offered the next version on it, unless you pin it to one version.
During the v3 alpha, the official interpreters are published on `alpha` only.

### Lifecycle state

What a publisher says about a version: `active` or `deprecated` (both
installable), or `unavailable` or `retired` (not installable). A plugin whose
version is retired after you install it keeps running; the dashboard marks it
with the publisher's reason.

## Building an app

### Instance

One running HappyView server, self-hosted or on HappyProto. Its role on the
atproto network is an AppView.

### App

Your own product, which talks to an [instance](#instance).

### Project

The directory you deploy to an [instance](#instance): its lexicons and scripts
under `src/`, its interpreters and libraries in `happyview.toml`, and the exact
plugin versions in `happyview.lock`. Run a project locally with
`hpy happyview dev`, check it with `check`, test it with `test`, and deploy it
to an instance with `hpy happyview deploy`. Deploying needs the
`project:deploy` permission. HappyView also runs a project directly when
`HAPPYVIEW_PROJECT` points at its directory.

### HappyProto project

A container in the HappyProto dashboard that holds one instance today and other
services later. Your [project](#project) deploys to the instance in a
HappyProto project.

### Service entry

A service an [instance](#instance) publishes in its DID document, and the id
other services use to address it.

### Third-party API client

A child API client an [app](#app) creates through
`dev.happyview.createApiClient`.

### hpy

HappyProto's command-line tool.

- `hpy happyview` builds HappyView apps: `create`, `dev`, `add`, `build`,
  `check`, `test`, `types`, then `login`, `deploy`, `logout` and `whoami` for
  instances.
- `hpy registry` signs in to the registry with `login`, and manages your
  plugins there with `hpy registry plugin`: `init`, `publish`, `status`,
  `lifecycle` and others.
- `hpy update` and `hpy channel` keep hpy itself up to date.

## Access

### Operator

A person who signs in to an instance's dashboard or admin API to run it. The
dashboard's **Users** page lists operators.

### User

A person signed in to an app with their atproto account.

### Permission

One thing an [operator](#operator) or API key may do, such as `lexicons:publish`
or `scripts:manage`. An operator holds any mix of them, often starting from a
[template](#template). The full list is under [Permissions](#permissions).

### Template

A starting set of [permissions](#permission) for a new operator: **Viewer**,
**Maintainer**, **Manager** or **Full Access**. Each includes everything in the
one before it.

### Superadmin

A privilege an operator holds: every permission, unrestricted. Usually one
operator has it; only an operator who holds it can transfer it to another, and
the dashboard marks them **Owner**. On a fresh instance it goes to the first
person to sign in, unless `SUPERADMIN_DID` names someone else.

### Permission set

An atproto OAuth permission set that an app asks for at sign-in to use an
instance's admin API. HappyView's is `dev.happyview.adminFull` ("Manage your
HappyView instances"), which grants `rpc` on `dev.happyview.admin.manage`. An app
holding it acts with the permissions the signed-in operator already has on that
instance, never more. `hpy` signs in with it.

### Space inspector

The dashboard pages and admin routes an operator uses to read private
[space](/docs/guides/spaces) contents while handling a report. It is off by
default, and reading needs `spaces:inspect` and an
[access grant](#access-grant). See
[Moderating spaces](/docs/guides/spaces#moderating-spaces).

### Access grant

Time-limited permission for one operator to read one space's contents, or one
account's records in every space, given with a reason. The grant and every read
under it are [protected events](/docs/guides/event-logs#protected-events).

## Lexicons

### Lexicon

A schema document describing a record type, a query or a procedure. A
**record lexicon**, **query lexicon** or **procedure lexicon** is named by its
`main` type.

### NSID

A lexicon's id, such as `xyz.statusphere.status`.

### Project lexicon

A [lexicon](#lexicon) defined by a file under a [project's](#project)
`src/lexicons/`.

### Network lexicon

A [lexicon](#lexicon) an instance fetches from its authority on the network and
keeps up to date.

### Uploaded lexicon

A [lexicon](#lexicon) added to an instance through the dashboard or the admin
API. The dashboard's **Local** tab adds one, and the API reports its source as
`manual`.

## Records

### Account

An atproto identity with its own repository. Backfill progress counts
accounts.

### Collection

The set of records of one record [lexicon](#lexicon), named by that lexicon's
[NSID](#nsid).

### Record provider

Where an instance's records come from and where they're kept. A provider is a
**record source**, a **record storage**, or both. Both are traits in the open
`happyview-provider` crate. A stock instance uses the built-in Jetstream source
and keeps everything in its own database.

### Record source

What finds records on the network and hands them to HappyView. The built-in one
is Jetstream, which also runs backfills.

### Record storage

Where the records of the collections it claims are kept, outside the instance's
own database. HappyView still runs record scripts, serves reads and handles
writes for those collections. If the storage can't be reached, record reads
answer `503` "the record store is unavailable" rather than an empty result.

### Backfill

Indexing the records a collection already has on the network, rather than
waiting for new ones to arrive. A backfill is a **crawl**, a **replay** or, on
HappyProto, a run of your record scripts over the network store's copy.

### Crawl

A backfill that lists accounts from the relay and fetches each account's
records from its PDS.

### Replay

A backfill that reads the Jetstream archive.

### Network store

The shared copy of public atproto records every HappyProto instance reads
from, through a record source and storage of HappyProto's own. If you run
HappyView yourself, it doesn't apply to you.

### Script stats

What a backfill's records cost in record scripts, reported in a backfill job's
`hook_stats`.
