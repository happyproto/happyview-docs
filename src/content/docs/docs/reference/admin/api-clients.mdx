import { Tabs, TabItem } from '@astrojs/starlight/components';

API clients identify third-party apps that call HappyView's XRPC endpoints. A caller names its client with an `X-Client-Key` header or a `client_key` query param. The client key is HappyView's rate-limit bucket: an anonymous request with no key shares one `anonymous` bucket, and an authenticated request with no key gets `401 Unauthorized`.

Create one API client for your app and use its client key in every instance. The client key identifies the app. Users sign in separately via OAuth.

Each client has an `hvc_`-prefixed client key. A confidential client also has one or more `hvs_`-prefixed client secrets ([Client secrets](#client-secrets)). A secret is returned only when it's created, and only its SHA-256 hash is stored. Server-to-server callers pass a secret as `X-Client-Secret`. Browser callers use the `Origin` header, which is matched against the client's `client_uri`. A request that matches neither is logged and handled as anonymous rather than rejected, and is not charged to the client's rate limit bucket. The same holds for a key HappyView doesn't know. A request made through the client's own session needs neither check. See [XRPC API client identification](/docs/reference/authentication#xrpc-api-client-identification) for the client-side view, and the [API keys guide](/docs/guides/api-keys) for how admin API keys differ from API clients.

:::tip[Third-party API clients]
Third-party apps can also create, list, and delete their own API clients programmatically via the [XRPC API](/docs/reference/oauth), without needing admin access.
:::

## List API clients

```
GET /admin/api-clients
```

Requires `api-clients:view`. Returns clients ordered by `created_at` descending. Secrets are never returned.

| Param       | Type   | Required | Description                                                  |
| ----------- | ------ | -------- | ------------------------------------------------------------ |
| `parent_id` | string | no       | Only clients whose `parent_client_id` is this id (query param) |

The list includes `builtin-hpy`, the public client hpy signs in with (`client_key` `hvc_hpy`). HappyView writes it at every boot, and updating it, deleting it, adding or revoking a secret, or provisioning or rotating an authentication key for it answers `409 Conflict`.

## Create an API client

```
POST /admin/api-clients
```

Requires `api-clients:create`. Generates a `client_key`, and for a confidential client a first `client_secret`, labelled `Original`. Store the secret: it won't be shown again.

| Field                    | Type     | Required | Description                                                                            |
| ------------------------ | -------- | -------- | -------------------------------------------------------------------------------------- |
| `name`                   | string   | yes      | Human-readable display name                                                            |
| `client_id_url`          | string   | yes      | URL to the client's published OAuth client metadata document                           |
| `client_uri`             | string   | yes      | The client's home/landing URL                                                          |
| `redirect_uris`          | string[] | yes      | Allowed OAuth redirect URIs                                                            |
| `scopes`                 | string   | no       | Space-separated OAuth scopes (default `"atproto"`)                                     |
| `client_type`            | string   | no       | `"confidential"` (default) issues a `client_secret`; `"public"` issues none. Anything else is `400` |
| `allowed_origins`        | string[] | no       | Browser origins allowed for this client                                                |
| `rate_limit_capacity`    | integer  | no       | Per-client token bucket capacity. Falls back to `DEFAULT_RATE_LIMIT_CAPACITY` if unset. Applies only when both rate-limit fields are given |
| `rate_limit_refill_rate` | number   | no       | Tokens added per second. Falls back to `DEFAULT_RATE_LIMIT_REFILL_RATE` if unset. Applies only when both rate-limit fields are given |

Returns `400 Bad Request` for an unknown `client_type`, and `409 Conflict` if `client_id_url` is a registered domain's OAuth client.

**Response**: `201 Created`. `client_secret` is omitted for a public client.

```json
{
  "id": "7c9e6679-7425-40de-944b-e07fc1f0d4c7",
  "client_key": "hvc_a1b2c3...",
  "client_secret": "hvs_d4e5f6...",
  "name": "My Game Client",
  "client_id_url": "https://example.com/client-metadata.json",
  "client_type": "confidential"
}
```

The new client is immediately registered with the OAuth registry and rate limiter, so it can authenticate without restarting HappyView.

## Get an API client

```
GET /admin/api-clients/{id}
```

Requires `api-clients:view`. Returns the same shape as the list endpoint, or `404 Not Found`.

## Update an API client

```
PUT /admin/api-clients/{id}
```

Requires `api-clients:edit`. All fields are optional, and a field left out is unchanged. `allowed_origins` and the two rate-limit fields also take `null`, which clears them. The rate limiter uses the client's own limits only while both fields are set; otherwise it falls back to the defaults.

## Delete an API client

```
DELETE /admin/api-clients/{id}
```

Requires `api-clients:delete`. Removes the client from the OAuth registry, the rate limiter, and the client identity store. It also revokes the client's authentication keys and deletes its child clients. Returns `404 Not Found` if the client doesn't exist.

## Client secrets

A confidential client can hold several secrets at once, each with a label and each revocable on its own. A public client has none: it is identified by its key and its `Origin`.

To rotate a secret, add a new one, move your callers to it, then revoke the old one. The client, its key and its sessions are untouched throughout.

### List secrets

```
GET /admin/api-clients/{id}/secrets
```

Requires `api-clients:view`. Lists every secret the client has held, revoked ones included, as `{ "secrets": [...] }`. The secrets themselves are never returned.

## AT Protocol client authentication keys

A client can delegate its AT Protocol OAuth signing key to HappyView, so HappyView authenticates to users' PDSes as a confidential client on its behalf. Confidential clients get far longer session lifetimes than public ones (the authorization server's policy: 2 years rather than 2 weeks on a conforming PDS).

Delegating takes two steps: provision a key here, then publish the fields it returns in the client metadata document served at the client's Client ID URL. Until both are done the client stays public, which is the default and requires no action.

The authorization server decides whether the client is confidential by fetching the app's published document. HappyView has no setting for it. These endpoints provision the key and report what that document currently says.

### Provision the key

```
POST /admin/api-clients/{id}/auth-key
```

Requires `api-clients:edit`. Generates an ES256 keypair for this client. Idempotent: it returns the current key if one is already provisioned.

### Rotate the key

```
POST /admin/api-clients/{id}/auth-key/rotate
```

Requires `api-clients:edit`. Mints a new key, staged the same way as the [instance key](/docs/reference/admin/oauth-keys#rotate-the-key). By default it is published as `pending` and becomes `current` after 75 minutes, when the previous key becomes `retiring`. Send `{ "immediate": true }` to switch at once; authorization servers that cached the old key set may refuse the new key until their cache expires. Rotating again without `immediate` while a key is pending returns that pending key, and a client with no current key gets its new key as `current` at once. Rotation logs nobody out: a retiring key stays in the published JWKS and keeps signing refreshes for the sessions established with it.

| Field       | Type    | Required | Description                                          |
| ----------- | ------- | -------- | ---------------------------------------------------- |
| `immediate` | boolean | no       | Make the new key `current` at once. Default `false`  |

```json
{
  "kid": "f0c3...",
  "status": "pending",
  "activates_at": "2026-08-29T11:29:02.000Z",
  "orphaned_sessions": 0
}
```

`status` is `pending` or `current`. `activates_at` is `null` when `status` is `current`.

### Revoke a key

```
DELETE /admin/api-clients/{id}/auth-key/{kid}
```

Requires `api-clients:edit`. Removes the key from the published JWKS immediately and strands every session pinned to it, and those users must re-authenticate.

Use this when a key has leaked or been compromised. Rotation doesn't contain a leak: the rotated-out key stays published and valid, which is what keeps existing sessions working. A retiring key with no remaining sessions is revoked automatically.

| Status | Meaning |
| ------ | ------- |
| `400`  | The target is the `current` key. Rotate with `{ "immediate": true }` first, then revoke the retiring key. |
| `404`  | No key with that `kid` belongs to this client. |

### Remove the key entirely

```
DELETE /admin/api-clients/{id}/auth-keys
```

Requires `api-clients:edit`. Revokes every key this client holds and leaves its JWKS empty, un-delegating it completely. Unlike the per-key revoke above, this one does take the `current` key, because it removes the whole keyset.

:::caution[Remove the published fields too, or the app breaks]
This does not downgrade the app to a public client. If its published document still advertises `token_endpoint_auth_method: "private_key_jwt"`, `token_endpoint_auth_signing_alg` and this `jwks_uri`, an authorization server will fetch an empty key set and reject the client outright, and `POST /oauth/client-assertion` will return `400`. The app stays broken until those three fields are removed from its published metadata too, so coordinate both halves.
:::

Returns `400` if the client already holds no key.

### Respond to a leaked authentication key

1. Rotate with `POST .../auth-key/rotate` and `{ "immediate": true }`. The leaked key becomes `retiring`, a fresh key takes over, and the client keeps working.
2. Call `GET .../auth-keys` and confirm the leaked key is `retiring`. Its `session_count` is how many sessions step 3 ends.
3. Revoke the leaked key with `DELETE .../auth-key/{kid}`.

The reverse order is refused: the current key cannot be revoked, because that would leave the client unable to authenticate at all.

To stop delegating altogether, so that HappyView holds no key, use `DELETE .../auth-keys` above, and remove the three published fields from the app's metadata document at the same time.
