HappyView keeps an event log of system activity: lexicon changes, record operations, script runs and errors, operator actions, API key events, backfills and Jetstream connectivity. Events are stored in the database and read from **System > Event Logs** or the [admin API](/docs/reference/admin/events).

## Event types

Events follow a `category.action` naming convention. Each event has a severity level (`info`, `warn`, or `error`), an optional `actor_did` (who triggered it), an optional `subject` (what was affected), and a `detail` JSON object with event-specific data.

### Lexicon events

| Event Type        | Severity | Subject      | Detail                             |
| ----------------- | -------- | ------------ | ---------------------------------- |
| `lexicon.created` | info     | Lexicon NSID | `revision`, `source`               |
| `lexicon.updated` | info     | Lexicon NSID | `revision`, `source`               |
| `lexicon.deleted` | info     | Lexicon NSID | `delete_records_job` and `records_at_delete` when its records are deleted too |
| `lexicon.published` | info   | Lexicon NSID | `did`, `uri`, `cid`                |
| `lexicon.publish_failed` | warn | Lexicon NSID | `error`                         |
| `lexicon.unpublished` | info | Lexicon NSID | `did`, `uri`                       |
| `lexicon_publishing.rule_created`, `.rule_updated`, `.rule_deleted` | info | The rule's pattern | `rule_id`, `target_kind`, `linked_repo_id`, `auto_publish` |

The first three are logged when lexicons are uploaded, updated, or deleted via the [admin API](/docs/reference/admin/lexicons). The `actor_did` is the operator who performed the action. The rest come from [publishing lexicons](/docs/guides/publishing-lexicons). A publishing failure that repeats the last error isn't logged again.

### Project events

| Event Type         | Severity | Subject               | Detail                   |
| ------------------ | -------- | --------------------- | ------------------------ |
| `project.deployed` | info     | The bundle's sha256   | `changes`, `backfills`   |

Logged when a project is deployed through [`PUT /admin/project`](/docs/reference/admin/project). A dry run logs nothing. `changes` and `backfills` are the ones the deploy answered with.

### Record events

| Event Type       | Severity | Subject       | Detail                                |
| ---------------- | -------- | ------------- | ------------------------------------- |
| `record.created` | info     | Record AT URI | `collection`, `did`, `rkey`           |
| `record.deleted` | info     | Record AT URI | `collection`, `did`, `rkey`           |
| `record.skipped` | info     | Record AT URI | `collection`, `did`, `rkey`, `reason` |
| `record.skip_ignored` | warn | Record AT URI | `collection`, `did`, `rkey`, `ignored`, `reason` |
| `record.cid_mismatch` | warn | Record AT URI | `collection`, `did`, `rkey`, `claimed_cid`, `reason` |
| `record.index_failed` | warn | Record AT URI | `error` |
| `record.unstored_claimed` | warn | Record AT URI | `collection`, `did`, `rkey` |
| `record.delete_hook_failed` | warn | Record AT URI | `origin`, `job_id`, `cid`, `error` |

Logged when records are received from Jetstream and stored or removed from the local database, or skipped because a record script returned `nil`. An update is logged as `record.created`. These are system-triggered events (`actor_did` is null). They write one row per record, so successful operations are only logged when [`verbose_event_logging`](/docs/reference/admin/settings) is on. If a database error occurs, the same event type is logged with `error` severity regardless of that setting, and the error message is included in the detail.

`record.unstored_claimed` is logged when a record of a collection that an [external record storage](/docs/guides/record-providers#claimed-collections) claims arrives from somewhere other than that storage. HappyView refuses it. `record.delete_hook_failed` and the `record.deleted` events whose `origin` is `happyview.reconcile-collection` come from the job that removes records their PDS no longer holds. That job logs every record it deletes, whatever `verbose_event_logging` says.

### Script events

| Event Type             | Severity | Subject                | Detail                                                                      |
| ---------------------- | -------- | ---------------------- | --------------------------------------------------------------------------- |
| `script.executed`      | info     | Method NSID            | `method`, `caller_did`, `duration_ms`, `response_size`, `input`, `response` |
| `script.error`         | error    | Method NSID            | `error`, `script_source`, `input`, `caller_did`, `method`, `duration_ms`    |
| `script.executed`      | info     | Record or label AT URI | `host_kind`, `host_id`, `trigger`, `attempts`                               |
| `script.dead_lettered` | error    | Record or label AT URI | `host_kind`, `host_id`, `trigger`, `error`                                  |
| `script.log`           | as logged | The script's trigger  | `trigger`, `level`, `message`, `fields`                                     |
| `script.created`, `script.updated` | info | Script id          | `script_type`                                                               |
| `script.deleted`       | info     | Script id              | none                                                                        |
| `script.codemod_applied` | info   | Script id              | `script_type`, `markers`                                                    |

For XRPC query and procedure scripts, `script.executed` is written on every call and stores the full request and response, so it is only logged when [`verbose_event_logging`](/docs/reference/admin/settings) is on. `script.error` is always logged, with what you need to reproduce the failure: the error message, the complete script source, the input that triggered it, and the caller's DID.

For [record and label scripts](/docs/getting-started/reacting-to-records), `script.executed` fires once per record or label that reaches a script, so it too is only logged when [`verbose_event_logging`](/docs/reference/admin/settings) is on. `script.dead_lettered` means a script failed all retry attempts; see [Dead letters](#dead-letters) below.

`script.log` is a line from `require("internal.logging")`, with the severity the script named. A `debug` line is never stored.

:::note
For query scripts, `input` and `caller_did` are left out of the detail, and `script.executed` carries `params` instead.
:::

| Event Type                 | Severity | Subject               | Detail               |

### Space events

| Event Type | Severity | Subject | Detail |
| --- | --- | --- | --- |
| `space.access_granted` | info | Space AT URI for a space grant, the DID for an account grant | `grant_id`, `scope`, `target`, `reason`, `expires_at`, `user_id` |
| `space.access_revoked` | info | As for `space.access_granted`, or the space id once the space is deleted | `grant_id`, `revoked_by`, `user_id` |
| `space.moderator_read` | info | Space AT URI, or the account's DID | `action`, `grant_id`, `scope`, `user_id`, and what was read (see below) |
| `space_inspector.enabled` | warn | `feature.space_inspector_enabled` | none |
| `space_inspector.disabled` | warn | `feature.space_inspector_enabled` | none |

These record access to private atproto space contents through the [space inspector](/docs/guides/spaces#moderating-spaces), and every one is a [protected event](#protected-events). `space.access_granted` and `space.access_revoked` record a grant's start and early end. `user_id` is the operator the grant belongs to, and `revoked_by` is the DID of the operator who ended it. `space_inspector.enabled` and `space_inspector.disabled` record the inspector being turned on or off, from the dashboard or the [settings API](/docs/reference/admin/settings).

`space.moderator_read` is logged when an operator reads space records or blobs through the [admin spaces API](/docs/reference/admin/spaces). `grant_id` is the [access grant](/docs/reference/admin/spaces#access-grants) the read was made under, and `scope` is its scope, `space` or `account`. `action` is one of these:

- `list_records`: includes `space_id`, the `repo` and `collection` filters, and the `uris` returned.
- `get_blob`: includes `space_id`, the blob `cid` and the `repo` that references it.
- `list_account_records`: its subject is the account's DID. It includes that `repo`, the `space_id` and `collection` filters, and the `uris` returned.

Listing spaces and viewing their metadata or members is not logged. In the dashboard, a `space.access_granted` event lists the reads made under that grant.

### Jetstream events

| Event Type                          | Severity | Subject     | Detail                                                                |
| ----------------------------------- | -------- | ----------- | --------------------------------------------------------------------- |
| `jetstream.connected`               | info     | none        | `url`, `protocol`, `compression`, `dictionary_id`                     |
| `jetstream.disconnected`            | warn     | none        | `reason`                                                              |
| `jetstream.stalled`                 | warn     | none        | `idle_secs`, `host`, `protocol`, `delivered`                          |
| `jetstream.stall_backoff`           | warn     | none        | `stalls`, `cursor`, `stall_timeout_secs`, `host`                      |
| `jetstream.gap`                     | warn     | none        | `reason`, and more by reason (below)                                  |
| `jetstream.invalid_request`         | error    | none        | `message`, `retry_in_secs`                                            |
| `jetstream.account_deleted`         | info     | Account DID | `purged`, `seq`                                                       |
| `jetstream.account_takendown`       | info     | Account DID | `purged`, `seq`, `status` (`takendown` or `suspended`)                |
| `jetstream.account_inactive`        | info     | Account DID | `status` (`deactivated`, `desynchronized` or `throttled`)             |
| `jetstream.account_status_mismatch` | warn     | Account DID | `status`, `pds`, `seq`                                                |
| `jetstream.sync_purged`             | info     | Account DID | `purged`, `rev`                                                       |
| `jetstream.record_invalid`          | warn     | Account DID | `uri`, `seq`, `error`                                                 |
| `jetstream.apply_failed`            | error    | Account DID | `uri` (or `kind` and, for an account event, `status`), `seq`, `error` |

`jetstream.connected` and `jetstream.disconnected` are logged when the WebSocket connection to [Jetstream](https://github.com/bluesky-social/jetstream) is established or lost.

`jetstream.stalled` is logged when a connection stays open but delivers no event for `JETSTREAM_STALL_TIMEOUT_SECS` (60 by default). It's never logged when that's `0`. HappyView closes it and reconnects from its saved position, so nothing is skipped. `idle_secs` is the timeout that was reached, and `delivered` says whether the connection had delivered any event before it went quiet. One now and then is harmless. Repeated ones point at the Jetstream host or the network path to it.

`jetstream.stall_backoff` is logged when a connection starts after one or more stalls in a row at the same position, none of which delivered an event. Jetstream sends nothing while it scans past events your collection filter drops, and a burst of millions of events from one repository can take it minutes to scan. So each such stall doubles the timeout for the next connection, up to 15 minutes, and an event delivered resets it. `stalls` is how many stalls came before this connection, `cursor` the position it resumes from, and `stall_timeout_secs` the timeout it waits. If it reaches 15 minutes and keeps stalling, the problem is the Jetstream host, not a slow scan.

`jetstream.gap` means events may have been missed. The same gap (same reason and cursor) is logged once per run of the Jetstream consumer. Its `reason` is one of:

- `cursor_too_old`: the saved cursor was past Jetstream's retention and no saved time could replace it, so HappyView resumed from the live tip. `after_seq` is the saved seq (the last one known applied), `resumed_at_seq` the first seq received after it, and `message` Jetstream's explanation. When HappyView replays the gap from the Jetstream archive instead, `resumed_at_seq` is the archive's sealed tip and `replay_job_id` names the [backfill](/docs/guides/backfill) job that fills the gap.
- `outdated_cursor`: Jetstream moved a time cursor older than its retention up to the oldest event it has. `message` names where it resumed.
- `future_cursor`: the saved seq was past Jetstream's newest, because its seq numbering restarted. HappyView reconnects by the saved witnessed time, which Jetstream translates to the new numbering, or, with none saved, follows the new numbering from the live tip. `from_seq` is the cursor it asked for.

`jetstream.invalid_request` means Jetstream refused the subscription as invalid, or kept refusing it without saying why after HappyView dropped what it could from the request. HappyView retries after `retry_in_secs` (an hour by default).

`jetstream.account_deleted` is logged when an account this instance holds records for is deleted: its records (other than local writes not yet echoed back) are removed. `jetstream.account_takendown` is logged the same way for an account that is taken down or suspended.

A tombstone is written for every deleted, taken-down or suspended account, but the event is logged only when this instance held, and purged, records for it. The tombstone means a late or replayed copy of the account's records is refused.

`jetstream.account_status_mismatch` is logged instead when the relay reports an account deleted (`status`) but the account's current PDS (`pds`) says it is active: HappyView keeps its records and writes no tombstone. This happens when the relay is still relaying a PDS the account moved away from. Takedowns and suspensions are never checked this way, because a relay may impose them without the account's PDS knowing.

`jetstream.account_inactive` is logged when such an account is deactivated, desynchronized or throttled; its records are kept. When an account becomes active again, its tombstone is lifted, but removed records come back only through a new [backfill](/docs/guides/backfill).

`jetstream.sync_purged` is logged when an account's repo is resynced: its records in registered collections are removed, and the current ones that follow in the stream replace them. Events for accounts this instance holds nothing for are not logged.

`jetstream.record_invalid` is logged once for an event HappyView skips immediately because retrying cannot help. That is a create or update with no record body, an unknown operation, data the database rejects, or a network lexicon schema that cannot be applied.

`jetstream.apply_failed` is logged when an event keeps failing for a reason that is not a database outage. HappyView retries it for about 31 seconds, logs this event and skips it, so one bad event does not stall the stream. Database outages are never skipped: see [Real-time indexing](/docs/architecture#real-time-indexing).

Saving a setting back to its current value logs nothing. Because protected retention can follow the general one, one change can log an event for each key. The setting and its event are saved together, so if the event can't be written, the setting isn't changed.

## Querying events

Use the admin API to query event logs with filters:

<TabItem label="TypeScript">

```ts
const TOKEN = "hv_..."; // your API key
const headers = { Authorization: `Bearer ${TOKEN}` };

interface Event {
  id: string;
  event_type: string;
  severity: string;
  actor_did?: string;
  subject?: string;
  detail: Record<string, unknown>;
  created_at: string;
}

interface EventsResponse {
  events: Event[];
  cursor?: string;
}

// Get all errors
const errors: EventsResponse = await fetch(
  "http://127.0.0.1:3000/admin/events?severity=error",
  { headers },
).then((r) => r.json());

// Get script errors for a specific lexicon
const scriptErrors: EventsResponse = await fetch(
  "http://127.0.0.1:3000/admin/events?event_type=script.error&subject=com.example.feed.like",
  { headers },
).then((r) => r.json());

// Get all lexicon-related events
const lexiconEvents: EventsResponse = await fetch(
  "http://127.0.0.1:3000/admin/events?category=lexicon",
  { headers },
).then((r) => r.json());

// Paginate through results
const page: EventsResponse = await fetch(
  "http://127.0.0.1:3000/admin/events?limit=20&cursor=2026-03-01T11:59:00Z",
  { headers },
).then((r) => r.json());
```

token := "hv_..." // your API key

get := func(url string) []byte {
	req, err := http.NewRequest("GET", url, nil)
	if err != nil {
		log.Fatal(err)
	}
	req.Header.Set("Authorization", "Bearer "+token)
	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		log.Fatal(err)
	}
	defer resp.Body.Close()
	body, err := io.ReadAll(resp.Body)
	if err != nil {
		log.Fatal(err)
	}
	return body
}

// Get all errors

## Retention

Event logs are automatically cleaned up after 30 days. Change that with **Event Log Retention (days)** under **System > General**, or the `EVENT_LOG_RETENTION_DAYS` environment variable; the setting wins. A background task runs hourly to delete events older than the retention period. Job logs and stored [script performance](/docs/guides/dashboard#script-performance) metrics follow the same period.

Set the value to `0` to disable automatic cleanup and keep logs indefinitely. [Protected events](#protected-events) have a retention period of their own.

See the [Configuration reference](/docs/reference/configuration#logging-retention-and-telemetry) for the other retention settings.

## Protected events

Some events record access to private atproto space contents, or changes to the audit trail itself. These are protected, and can't be purged by hand:

- `space.access_granted`
- `space.access_revoked`
- `space.moderator_read`
- `space_inspector.enabled`
- `space_inspector.disabled`
- `event_logs.purged`
- `event_logs.retention_changed`

A [purge](/docs/reference/admin/events#purge-event-logs) skips them. A purge filter naming one of these types, or a category holding one, answers `400 Bad Request`. The purge preview, `GET /admin/events/count`, doesn't count them either.

They're removed only by their own retention, `space_access_log_retention_days`. It's set under **System > General** as **Space Access Log Retention (days)**. It is 365 days by default, and `0` keeps them. While it is unset, a general retention of `0` makes it `0` too. The same hourly cleanup deletes access grants that ended longer ago than that.

Events tied to an access grant that still exists are kept whatever their age: its grant and revocation events and the reads made under it. So a grant's reason and reads last as long as the grant does. Other protected events follow their own retention period.

Protected events live in the same database table as every other event. This guards against a routine or accidental purge, but it isn't a tamper-proof audit log. Anyone with direct access to the database can still delete them.

A hosting platform can [fix this retention](/docs/reference/configuration#settings-a-hosting-platform-fixes), and then it can't be changed from the dashboard or the API.

## Dead letters

When a record or label script fails after all retry attempts, the event is stored as a dead letter. You can manage dead letters from the **Data > Dead Letters** page in the dashboard.

From the dead letters page you can:

- **Retry**: replay the stored event through the script (use after fixing the script)
- **Re-index**: fetch the record fresh from the PDS and run it through the full indexing pipeline (use when the record may have changed)
- **Dismiss**: mark the dead letter as resolved without retrying

Bulk actions are available for selected rows or all entries matching the current filters.
