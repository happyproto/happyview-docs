Manage the ES256 key HappyView signs OAuth client assertions with. As a confidential OAuth client, HappyView authenticates to PDSes with `private_key_jwt` rather than as a public client, which earns its sessions the 2-year lifetime cap instead of 2 weeks. All endpoints require the `settings:manage` permission.

Every session records the `kid` of the key that established it, and is refreshed with that key even after a newer key becomes current. An authorization server destroys a session whose refresh carries a mismatched `kid`, so this pinning is what keeps sessions alive through a rotation.

Rotating and revoking a key have different consequences:

- **Rotate** mints a new key, which becomes `current` after 75 minutes (or at once with `immediate`) and marks the previous one `retiring`. A retiring key stays published in the JWKS and keeps signing every session established with it, so nothing is logged out.
- **Revoke** removes a key from the JWKS immediately and permanently breaks every session pinned to it. Use it for a leaked or compromised key.

Because of that difference, the current key cannot be revoked: that would leave the instance unable to authenticate to any PDS at all. To contain a leaked key, rotate first with `{ "immediate": true }` (which demotes the leaked key to `retiring` and mints a fresh `current`), then revoke the retiring key.

## List keys

```
GET /admin/oauth/instance-key
```

Returns every key the instance holds, ordered `pending`, `current`, `retiring`, then `revoked`. Revoked keys are included deliberately, so an operator can confirm a revoke took effect.

`session_count` is the number of live sessions pinned to that key, counted across the dashboard, linked-repo, and DPoP session tables. A revoked key keeps its count, because revoking doesn't delete session rows, so the count tells you how many sessions that revoke ended.

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
interface InstanceKey {
  kid: string;
  status: "pending" | "current" | "retiring" | "revoked";
  created_at: string;
  // When a pending key becomes current; null otherwise.
  activates_at: string | null;
  session_count: number;
}

const response = await fetch(
  "http://127.0.0.1:3000/admin/oauth/instance-key",
  { headers },
);
const data: { keys: InstanceKey[] } = await response.json();
```

## Rotate the key

```
POST /admin/oauth/instance-key/rotate
```

Mints a new key. By default it is published as `pending` and becomes `current` after 75 minutes, when the previous key becomes `retiring`. Send `{ "immediate": true }` to switch at once; authorization servers that cached the old key set may refuse the new key until their cache expires. Rotating while a key is pending returns that pending key, and with `immediate` makes that pending key `current` rather than minting another. An instance with no current key gets its new key as `current` at once.

Nothing is logged out: the retiring key stays in the published JWKS and keeps signing refreshes for every session established with it. New sessions use the new key once it is current.

| Field       | Type    | Required | Description                                          |
| ----------- | ------- | -------- | ---------------------------------------------------- |
| `immediate` | boolean | no       | Make the new key `current` at once. Default `false`  |

`status` is `pending` or `current`. `activates_at` is when a pending key becomes current, and is `null` when `status` is `current`.

`orphaned_sessions` counts sessions that predate key pinning and therefore carry no recorded `kid`. These cannot be protected by this or any future rotation.

## Revoke a key

```
DELETE /admin/oauth/instance-key/{kid}
```

Removes the key from the published JWKS immediately and destroys every session pinned to it, so whoever held one of those sessions must log in again. Use this when a key has leaked. Old keys need no manual revoke: an hourly cleanup revokes every retiring key that no session is pinned to.

`sessions_destroyed` reports how many sessions the revoke invalidated.

Errors:

| Status | Meaning |
| ------ | ------- |
| `400`  | The target is the `current` key. Rotate with `{ "immediate": true }` first, then revoke the retiring key. |
| `404`  | No unrevoked key with that `kid` belongs to this instance. |

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
interface RevokeResult {
  kid: string;
  sessions_destroyed: number;
}

const response = await fetch(
  `http://127.0.0.1:3000/admin/oauth/instance-key/${kid}`,
  { method: "DELETE", headers },
);
const data: RevokeResult = await response.json();
```

## Responding to a leaked key

1. `POST /admin/oauth/instance-key/rotate` with `{ "immediate": true }`. The leaked key becomes `retiring`, a new key (the pending one, if a rotation was waiting) becomes `current`, and the instance keeps working throughout.
2. `GET /admin/oauth/instance-key`. Confirm the leaked key is now `retiring` and note its `session_count`, which is how many sessions step 3 will end.
3. `DELETE /admin/oauth/instance-key/{kid}` on the leaked key.

Doing this in the other order is refused, because the current key cannot be revoked.
